# Create a journey from GPX recordings

**Implemented behind opt-in flags · 23 November 2026.** Bring several recordings of the same trip into one private journey. Review the route and suggested journey details before creating it. A typical timed GPX batch requires no date, time, title, or timezone entry. This plan updates the new-journey entry and recording count in the [current GPX implementation plan](gpx-journey-import.md).

The [current journey creation workflow](journey-creation-workflow.md) defaults to Upload GPX and offers Enter details in the same screen. It reuses the batch review and save described here.

## One creation page

1. **Enter.** Use the same primary **Create a journey** action on Dashboard and Journeys, including empty and populated states. Both open `/journeys/new` on web, iPhone, and Android. Keep access independent of recording-list availability. Move unfinished new-journey imports into the creation screen and preserve access to old drafts. From a saved journey, **Add recording** still opens that journey’s attachment flow.
2. **Choose.** Lead with **Add GPX files** and a **Choose files** button. Support drag and drop and multi-select on web, and use the system document picker on iPhone and Android. Additional selections append to the list. Each row shows the filename, size and **Remove**. The initial state is **On this device**. Files stay on the device and the screen does no GPX parsing at this stage.
3. **Review.** **Upload for review** is the explicit consent to transfer the selected files to private storage and process them. Show acknowledged-byte progress and then **Reading recording** for each file. Put the file list on the left and the route preview on the right on wide screens. Start with a quiet preview panel that says when the route appears. Draw each ready file in the interactive map automatically, with a selected file emphasised by line weight as well as colour. Stack the summary and preview below the files on narrow screens. Keep a text list of sections, times and issues usable with the map hidden or unavailable. Follow Fold spacing, surfaces and focus states.
4. **Save.** Show a compact summary of the suggested title, recorded start, recorded end and display timezone. Make **Save journey** the primary action once the included files are ready and any rejected items have been addressed. Allow an optional inline rename and selected details corrections. Save one private journey and open its canonical detail. Keep the option to **Plan without a recording** as a quiet action inside this same page for existing planning and onboarding users. It opens the current schedule controls in place.

The first implementation uses the [Kibo UI Dropzone registry component](https://www.kibo-ui.com/components/dropzone), which uses [React Dropzone](https://github.com/react-dropzone/react-dropzone) for the picker and drop events. Adapt it into the owned `base-nova` primitives and use the existing Button, Field, Alert and Progress components. Own the accumulated file list, rejection messages and removal in the journey draft. Check the imported source and dependency diff and show the shared dropzone states in `/design-system`. [Fold](../../DESIGN.md) · [Registry source](https://www.kibo-ui.com/r/dropzone.json)

## File selection and upload

- Use `.gpx` in the picker and validate the extension case-insensitively after selection. Accept GPX reported with generic, XML, or absent MIME types. Reject empty files, files over 50 MiB, and unsupported extensions per row. A file named `.gpx` can still fail content validation after transfer. Keep accepted siblings when a selection contains rejected files. Use the existing 500,000-point worker limit per file. Propose configurable starting batch limits of 10 files and 200 MiB, with the same enforced policy on every client and the server. Tune these limits with mixed-workload measurements. [Existing GPX limits](../../packages/contracts/src/recording-limits.ts)
- Keep selection metadata local until **Upload for review**. At that point, prepare the byte length and SHA-256 per file without buffering the whole batch, and use the existing authenticated, resumable multipart transport. Enforce a shared concurrency budget across the batch, starting with the existing two in-flight part limit per account in each gateway process and a matching client limit. Honour the native Wi-Fi preference. One file can finish and enter review while another is transferring. Use stable draft and file IDs to resume and fail each file independently. Detect identical files by verified content within the owner’s account. Same-name files with different contents can coexist. [Upload service](../../packages/backend/src/modules/recordings/uploads.ts)
- Keep self-hosted **SeaweedFS** behind Kairn’s private S3-compatible adapter. The local and deployment configurations already pin SeaweedFS 4.53. Use the API to authorise access to originals and previews. Keep the bucket private. Treat provider lifecycle rules as a backstop for abandoned staging after verifying behaviour on the pinned image. [Kairn storage decision](../core/architecture.md#11-architecture-decisions) · [SeaweedFS S3 operations](https://github.com/seaweedfs/seaweedfs/wiki/Amazon-S3-API)

| When someone removes a file | Result |
| --- | --- |
| Selected on the device | Remove the row and release any Kairn-managed local copy. The selected original stays in the provider’s Files or Downloads location. |
| Queued or uploading | Cancel the local request and record removal on the server. Abort the multipart upload and release the reservation after cleanup. |
| Uploaded, processing or ready | Revoke this draft’s access immediately, remove its map line and recalculate the suggestion. Discard queued or late results for the removed file. Queue deletion of unreferenced staged objects and derivatives, with retries and expiry reconciliation. An original already referenced by another draft or saved journey keeps those references. |

The existing single-file completion creates a durable owner recording, and abort returns a conflict on a completed upload. Add cancellable draft ownership for batch files so their cleanup applies after upload and before save. Persist cancellation before scheduling storage cleanup. Reconcile completion racing removal and account changes. Show when an unfinished draft expires and offer reselection when the client has lost access to an unsent file. Qualify the retention window for completed staging before enabling the new flow. Keep permanent deletion of previously retained originals under the existing recovery policy. [Current completion and abort](../../packages/backend/src/modules/recordings/uploads.ts) · [Recording recovery policy](gpx-journey-import.md#rights-interruption-and-recovery)

## Processing, map and inferred details

**Use the existing backend worker for authoritative GPX parsing.** It already validates GPX contents, splits continuous runs, measures recorded geometry and supports bounded review reads. Queue processing as each verified object finishes. Build the draft preview from small, owner-authorised simplified overlays. Preserve segment breaks and distinguish files when tracks overlap. Keep full-resolution measurement and source data on the server. The accepted 500,000-point fixture used 488 MiB peak resident memory on the local worker, so browser parsing would need its own memory qualification even if moved off the main thread. Measure upload-to-first-preview and total review time with realistic files and throttled uplink before considering an opt-in local preview. [Existing measurements](gpx-journey-import.md#implementation-evidence) · [Web Worker execution model](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)

Use the current Mapbox integration with scoped public tokens and attribution. Mount it when the first authorised path is ready, use a bounded aggregate overview at first and request more detail through the existing overlay boundary. On web, draw the authorised route locally when Mapbox is unconfigured or unavailable. Select a file or section from the list to highlight its route. Treat the preview as optional, dispose it on exit and remove stale paths after account changes or file removal. The viewport goes through the basemap provider and GPX originals stay in private Kairn storage. [Web route preview](../../apps/web/src/components/recordings/route-preview.tsx) · [Map provider boundaries](../core/architecture.md#121-selected-mapbox-integration)

| Journey field | Derivation |
| --- | --- |
| Title | Use a usable GPX metadata or track name from the first included file in selection order. Fall back to the cleaned filename stem, then **Recorded journey**. Keep the suggestion stable across worker completion order. Support an optional rename. The worker already retains track names. Add bounded document-name extraction to support metadata titles. |
| Start and end | Use the earliest and latest trustworthy recorded track-point instants in the included sections. Keep the exact source values separately and initialise the journey’s existing minute-precision schedule from the suggestion. When the recording window is incomplete or ambiguous, show known times as recording evidence and allow saving an undated journey or supplying a correction. Recording dates may cover only part of the trip. Label the suggestion **Recorded window** and reopen the existing schedule controls if the person wants to set the whole-trip dates. |
| Timezone | Preserve the recorded offsets. Use **UTC** as the labelled display timezone for resolved timestamps unless the person chooses a named zone. GPX does not guarantee an IANA timezone, and a numeric offset cannot identify one. Keep offset-free timestamps unresolved until an explicit correction can resolve them. |

GPX 1.0 and 1.1 can omit names and point times. Preserve untimed valid geometry and support an undated journey through the existing nullable schedule representation. Use a distinct batch-backed creation operation with a server-derived schedule, so planned journey creation can keep its existing required start and timezone rules. Planned-route and waypoint-only files get a clear unsupported-recording message. [GPX 1.0 manual](https://www.topografix.com/gpx_manual.asp) · [GPX 1.1 schema](https://www.topografix.com/GPX/1/1/) · [Journey contracts](../../packages/contracts/src/journeys.ts)

Save with one idempotent command that pins the draft and the selected review revisions. Recheck ownership, current asset policy and inclusion under the same transaction that creates the journey, its owner membership and all recording associations. Reuse the verified objects and source identity where eligible. A retry after a lost save response opens the same journey. Keep files separate for ownership and review. Overlapping tracks appear together in the preview, with no summed journey distance or fabricated connection across gaps. [Existing single-recording command](../../packages/contracts/src/recordings.ts)

## Implementation evidence

- **Web entry and staging.** Chromium and WebKit passed shared navigation, picker and drag-and-drop checks with local metadata and zero upload requests before consent. Chromium passed keyboard and accessibility checks at 320 CSS px and 200% text. Four live Chromium checks also passed with the redesigned entry disabled, including attachment to an existing journey. [Local staging](../../tests/web/create-journey-gpx.playwright.ts) · [Existing import and attachment](../../tests/web/recording-import.playwright.ts)
- **Transfer, review and save.** Two live scenarios each passed in Chromium and WebKit, including an interrupted transfer, removing an uploaded recording, restoring a batch on reload and reopening one journey after losing the save response. Fourteen isolated PostgreSQL and SeaweedFS checks passed, including expiry, cross-account access, duplicate review conflicts, nullable schedules, original retention and bounded response sizes for a 500,000-point recording. [Live browser scenarios](../../tests/web/recording-batch.playwright.ts) · [Service scenarios](../../tests/integration/recording-imports.test.ts)
- **Web route fallback.** A supplied 25,504-point recording rendered as a 512-point route overview in the live preview without a Mapbox token. Web recording review reuses the same renderer for new batches, imports and saved recordings. The interactive basemap requires a scoped `VITE_MAPBOX_PUBLIC_TOKEN` at build time. [Web route renderer](../../apps/web/src/components/recordings/route-preview.tsx) · [Build configuration](../../apps/web/.env.example)
- **Native.** The iPhone 18 Pro simulator and Android 17 emulator both selected multiple local GPX files in their system pickers, reopened a draft after relaunch and saved a private journey showing two recordings. Android also removed a transferred recording before save. Both displayed the map-free section list and opened the picker at Accessibility Large. Providers that omit the file size prompt the user to save a local copy before trying again. Workspace checks, 102 unit tests, OpenAPI parity and the web, Android and iOS builds passed. [Mobile flow](../../apps/mobile/src/components/journeys/create-recordings.tsx) · [Device picker and transfer](../../apps/mobile/src/recording-batch.ts)

### Before default rollout

- Enable test-scoped Mapbox tokens and verify interactive paths, selection and attribution on all three clients. Qualify the native fallback with provider failures.
- Run the physical iPhone, Android and mobile Safari walkthroughs. Cover cloud-backed selection, VoiceOver, TalkBack, large text, Wi-Fi-only transfer, transfer interruption, and appearance variants. The local Firefox runner stopped at launch with `Could not find profile folder`.
- Measure upload-to-preview latency and peak memory for multiple representative exports under throttled networking. Complete the release retention and worker checks. [GPX release qualification](gpx-journey-import.md#pending-work)
- Add optional in-creation corrections for whole-trip dates and named timezones. The first implementation supports renaming and saving with the derived UTC schedule or an undated schedule when the recorded window is unresolved.

The web flag is `VITE_GPX_JOURNEY_CREATE=1`. The native flag is `EXPO_PUBLIC_GPX_JOURNEY_CREATE=1`.
