## The first minute

Show two short setup screens after the first verified sign-in. Help the person understand that journeys start private and find the first useful action on their Dashboard. Keep the first session brief and teach trip details where the user enters them.

| Step | What the person sees | What changes |
| --- | --- | --- |
| **1. Welcome to Kairn** | A short privacy explanation and the display name from signup. **Edit name** opens an inline editor. A framed ferry illustration sits beside the welcome on wide web screens. | An edit saves to the same profile available in Account. **Continue** confirms the welcome step. |
| **2. What would you like to do first?** | A single column of choices for **Plan a journey**, **Record a past journey** and **Look around**. **Go to Dashboard** completes setup. A validated return destination has a button naming that destination. | A planning or recording choice changes the empty Dashboard and its journey creation guidance. **Look around** opens the standard Dashboard. |

Web setup shares the [Fold account entry frame](../../apps/web/src/components/account-entry-frame.tsx) with sign-in and adds an **Account** link. On narrow screens, omit the decorative artwork so the welcome and actions start near the top. Show the current position above each heading and move focus to the new heading after a transition. **Back** revisits the welcome. Account offers **Resume setup**.

Use the existing journey form for both planning and recording. Put the private visibility note next to **Save journey** and link the first Dashboard action to the correct date guidance. The display name and the first-journey choice are enough for this setup. Avatar and bio belong in Account when available. Journey activity type belongs in the journey form once it can be saved and edited. Age eligibility requires a separate product decision.

## Entry, resume and return

The [web account access milestone](web-account-access.md) defines the signed-out web experience.

| Entry | Expected outcome |
| --- | --- |
| Signed-out web entry, including Discover and Story | Open Sign in. Registration, email verification and password recovery remain available through Account. |
| Verified account with an incomplete walkthrough | Open the first unconfirmed step before any protected workspace content renders. New starts open Step 1. Reload, sign-out, a new browser or app reinstall resumes from the account’s server checkpoint. |
| First verified sign-in with a protected deep link | Preserve the validated target during the walkthrough. Offer a labelled continuation on the final step, persist completion, then recheck access on entry. If the person chooses Dashboard, clear the saved target when setup is complete and Dashboard opens. Links whose underlying access expired or was revoked get the ordinary unavailable state and a route to Dashboard. |
| Returning verified account that completed the walkthrough or was exempted at rollout | Ordinary sign-in and the workspace home/logo go to Dashboard. A valid explicit deep link resumes directly. Opening Account while already signed in stays in Account. |
| Session checking, expired, revoked or recovery-blocked | Reuse the neutral checking, sign-in and recovery states. A failed onboarding lookup offers retry and an account exit. Hold protected views while state is unknown. |

**Eligibility.** Keep the onboarding state in the application’s identity domain. Deploy the schema and supporting clients before activating enrollment with one server-side cutoff. Treat accounts verified by activation as established. After activation, classify the first successful verified sign-in atomically under the account lock. A client declaring walkthrough support starts the account at Step 1. A first sign-in on an older client records an exemption so a later upgrade will open Dashboard without introducing a belated tour. The capability marker only selects the UX. Failed sign-ins, verification alone, password resets and further sign-ins leave an assigned state intact. Existing sessions on old clients keep working during rollout.

**Return handoff.** Extend the [web return validator](../../apps/web/src/lib/journey-return.ts) and [native Account return path](../../apps/mobile/src/app/account.tsx) to keep one typed, allowlisted destination for an explicit sign-in request per originating browser tab or device. Capture it before sign-in, attach a proposed 24-hour expiry, and bind it to the verified account when the corresponding sign-in flow succeeds. The Account form or its verification return can resume that unbound flow. An unrelated generic sign-in discards an unbound intent. The verification callback itself remains fixed. A bound handoff can survive walkthrough interruption and same-account reauthentication on that client. Clear it when the target or its unavailable screen opens, when the chosen Dashboard exit completes, when it expires, or on a confirmed account switch. A new targeted sign-in replaces the previous handoff. Use Dashboard when a target cannot be recovered or validated. Keep raw URLs, bearer credentials and email out of return storage. Reauthorize on destination entry before resuming any protected action.

**Progress.** Each **Continue** confirms the current step and advances one checkpoint. **Back** revisits steps locally. From an earlier step, Continue moves forward through the already cleared steps without a write. On reload resume from the furthest confirmed checkpoint. Send the account precondition on protected reads and writes and scope progress to the current verified session in the transaction. Persist completion before routing and keep it terminal. While a write is pending show a saving state. On error retain the current screen and let the person try again. Already-confirmed operations return the current state, future-step jumps are rejected, and stale clients re-read it. A lost finish response can use the confirmed result to resume the chosen destination. The final confirmation persists the selected intent alongside completion in the same account transaction. The existing name is read and edited through the verified account profile API. The previous second and third checkpoints both resume on the intent screen. Completed and exempt accounts open Dashboard directly. The guard controls workspace navigation. Domain permissions continue to depend on the existing authorization checks. Keep Account, verification and reset available throughout.

## Dashboard and navigation

The web workspace exposes **Dashboard**, **Journeys**, **Discover** and **Saved** in a sidebar from 48rem and in a bottom bar below 48rem. The active destination has a stronger label and a selection marker, including inside journey routes. The sidebar starts expanded at 80rem and uses an icon rail with tooltips between 48rem and 80rem. Both desktop widths remember the user’s choice independently. The header identifies the current location and keeps the signed-in profile menu available across widths. The menu offers **Account**, **Appearance** with the current mode, and **Sign out**. On native **Dashboard** is the first labelled destination beside Journeys, Discover and Saved. **Journeys** provides full history and creation on all platforms.

The web Dashboard offers the existing journey creation route through one primary action. The illustrated empty state uses the first-journey choice when saved. After a journey is added, give the next journey the largest region, then show a compact overview and up to three recent rows. On narrow screens, use the same reading order in one column. Link rows to the canonical journey and **All journeys** to history.

The web shell passes routed content through the layout as a stable React child. Sidebar state lives in the shadcn provider, and the child routes keep their own queries and form state across width changes. [Workspace layout](../../apps/web/src/components/workspace-layout.tsx) · [Sidebar regression](../../tests/web/workspace-sidebar.playwright.ts)

| Region | First release |
| --- | --- |

| **Overview** | **Journeys** counts distinct journey IDs with current membership, including archived journeys. **Upcoming plans** counts the same non-archived future set used by **Next journey**. History keeps future archived entries in **Upcoming** by date and marks each **Archived**. Fetch authoritative totals even when history spans pages. |

For a new account, show the create action and a short explanation of what will appear after creating a journey. ### Web workspace redesign

The previous header contained the navigation toggle and left the current location to the page body. On a narrow screen the account menu required opening the navigation drawer first. The empty Dashboard gave two zero totals a full card beside the first task. The current summary supplies the nearest future journey, two authoritative totals and up to three recent journeys, which is enough for a compact overview.

1. **Workspace shell.** Group the desktop sidebar toggle and current location in the sticky header, with a Journeys breadcrumb on child routes. Put the profile at the trailing edge across desktop and phone widths. Show the name and email inside its menu. Use a single Appearance row that opens the shared chooser. Preserve the two collapse preferences and use the four labelled destination links in the phone-width bottom bar. Account and sign-out keep their existing routes and session behavior. [Carbon profile menus](https://www.carbondesignsystem.com/building-blocks/core/patterns/disclosures) · [WAI menu button behavior](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/)
2. **Dashboard.** Show one first task and the private default for an empty account. The open travel notebook and contour map illustrate starting a record. Place the artwork alongside the copy on wide layouts and leave narrow layouts to the task. Once journeys exist, show the next scheduled journey and actual totals first. Put recent journeys below in a date-led list with archived and undated states. Loading has a stable layout and errors offer retry. [Carbon first-use empty states](https://www.carbondesignsystem.com/building-blocks/core/patterns/empty-states)
3. **Validation.** Walk through first sign-in, all three setup choices, a populated summary, no upcoming journey, and summary retry. Check the menu through pointer and keyboard, sign-out and retry, navigation focus, preserved form drafts, appearance changes, and reflow at 320 CSS px and 200% text. Compare both Dashboard states in the running app and review the implementation independently before closing the milestone.

## Implementation sequence

1. **Agree the surface and examples.** Prototype both setup screens and Dashboard at desktop and phone widths under the approved tokens. Check copy, progress, the small-screen action order and the pending-return path. Record the accepted navigation and first-run rules in the application design and product requirements.
2. **Ship account state and Dashboard summary contracts.** In the identity domain, add the schema ahead of activation, eligibility classification at verified sign-in, and scoped, idempotent progress operations. In the Journey domain, add a bounded Dashboard read reusing the [active membership query](../../packages/backend/src/modules/journeys/service.ts) and schedule rules. Use one snapshot and one `asOf` for the totals and rows. Follow the existing protected [HTTP wiring](../../apps/server/src/http/v1.ts), response and cache rules. Keep API additions compatible with deployed clients.
3. **Implement web.** Add a single routing policy for home, sign-in return and guarded routes. Update the [root shell](../../apps/web/src/routes/__root.tsx), [home](../../apps/web/src/routes/index.tsx) and [account sign-in](../../apps/web/src/routes/account.tsx). Use the existing session provider and return validator as the starting point. Render welcome and intent first, then Dashboard and the updated shell. Bind pending requests and summary data to the active account and clear private data when that scope changes.
4. **Implement iPhone and Android.** Add the same checkpoints, Dashboard and contextual return rules using the [mobile session provider](../../apps/mobile/src/mobile-session.tsx) and [root navigation](../../apps/mobile/src/app/_layout.tsx). Use the approved native controls, safe areas and accessibility text scaling. Keep the content and interaction equivalent across platforms.
5. **Verify, then activate.** Use existing service-backed suites and place new regression fixtures under `tests/`. Record the actual results in this plan and [implementation progress](../progress.md). Activate enrollment once the supported clients are ready. Resume invitations once this milestone is accepted, then connect people data when membership privacy and revocation checks pass.

### Navigation and recovery

1. Keep the root navigator mounted. Gate the tab content while the session or onboarding checkpoint is unresolved, with Account reachable to sign in, retry or sign out. Use the actual internal route to capture a supported explicit link before redirecting. Normal launches and sign-ins use Dashboard. Bind a pending handoff at successful sign-in, clear it on a confirmed account switch or expiry, and consume it once the destination opens. A verified user can open Account during setup and return to setup.
2. On foreground revalidation, temporarily conceal private UI and block writes while retaining the same verified account subtree. Do not key tab navigation by transient loading state or change an Expo protected-route guard during foreground checks, since a false guard removes history. A confirmed scope change disposes that account’s queries and private screens. Retry the onboarding query when it fails and show Account as an exit. ### Astra review and decisions

The Astra review required a single navigation owner, explicit write recovery, and stronger device acceptance. Use the root workspace coordinator in place of Account’s current return effect. Capture only the first blocked explicit route, validate its type and allowed parameters before saving and reading, and bind it once when the verified account matches the successful sign-in. Opening the destination consumes it. A pending setup may keep its bound return over interruption for that same account, per the product flow. A different verified account, expiry, or an explicit Dashboard choice clears it. Losing access to a previously opened route does not capture that route again.

A confirmation response may already reflect a later step or another client’s completed choice. Read after a conflict or an uncertain response before retrying. Accept the server checkpoint and intent, and only retry a still-pending matching step. Reconcile an uncertain name save separately and retain the draft when the saved name differs. Refresh Dashboard and checkpoint on foreground and Dashboard on reentry. Refresh the profile on reentry without replacing a local edit. Keep still-verified children mounted while the foreground check runs, visually hidden and out of the accessibility tree. If verification fails, use the existing disposable scope and account recovery flow.

Run the real verification and first capable email sign-in with a fresh identity and a configured cutoff on the installed iPhone and Android development clients. Exercise native incoming URLs and account isolation. Use held requests and dropped replies where the test environment can reproduce them and record the operating system and evidence for each run. Physical VoiceOver requires separate evidence.
