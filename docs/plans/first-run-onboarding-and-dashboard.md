# First-run onboarding and Dashboard

**Reviewed plan · 20 November 2026.** This milestone comes before invitations and extends Kairn’s approved design system. Build responsive web first, then iPhone and Android with the same account state and flow. See the [product requirements](../core/product-requirements.md#3-account-profile-and-private-history), [application design](../core/application-design.md#2-navigation-and-entry-points) and [design foundations](../core/design-system/design-system-foundations.md).

## The first minute

Show two short setup screens after the first verified sign-in. Help the person understand that journeys start private and find the first useful action on their Dashboard. Keep the first session brief and teach trip details where the user enters them.

| Step | What the person sees | What changes |
| --- | --- | --- |
| **1. Welcome to Kairn** | One coastal illustration, a short explanation and the display name from signup. **Edit name** opens an inline editor. | An edit saves to the same profile available in Account. **Continue** confirms the welcome step. |
| **2. What would you like to do first?** | **Plan a journey**, **Record a past journey** and **Look around**. **Go to Dashboard** completes setup. A validated return destination offers its own continuation. | A planning or recording choice changes the empty Dashboard and its journey creation guidance. **Look around** opens the standard Dashboard. |

Keep the Kairn wordmark, appearance control and **Account** link visible. On wide screens, put the welcome illustration beside the title and profile. Give the intent question and options distinct columns. Stack the content in reading order on narrow screens. Show the two steps and the current position above the panel. Move focus to the new heading after a transition and respect reduced motion. Back revisits the welcome and Account offers **Resume setup**.

Use the existing journey form for both planning and recording. Put the private visibility note next to **Save journey** and link the first Dashboard action to the correct date guidance. The display name and the first-journey choice are enough for this setup. Avatar and bio belong in Account when available. Journey activity type belongs in the journey form once it can be saved and edited. Age eligibility requires a separate product decision.

## Entry, resume and return

The [web account access milestone](web-account-access.md) defines the signed-out web experience.

| Entry | Expected outcome |
| --- | --- |
| Signed-out web entry, including Discover and Story | Open Sign in. Registration, email verification and password recovery remain available through Account. |
| Verified account with an incomplete walkthrough | Open the first unconfirmed step before any protected workspace content renders. New starts open Step 1. Reload, sign-out, a new browser or app reinstall resumes from the account’s server checkpoint. |
| First verified sign-in with a protected deep link | Preserve the validated target during the walkthrough. Offer a labelled continuation on the final step, persist completion, then recheck access on entry. If the person chooses Dashboard, clear that intent. Links whose underlying access expired or was revoked get the ordinary unavailable state and a route to Dashboard. |
| Returning verified account that completed the walkthrough or was exempted at rollout | Ordinary sign-in and the workspace home/logo go to Dashboard. A valid explicit deep link resumes directly. Opening Account while already signed in stays in Account. |
| Session checking, expired, revoked or recovery-blocked | Reuse the neutral checking, sign-in and recovery states. A failed onboarding lookup offers retry and an account exit. Hold protected views while state is unknown. |

**Eligibility.** Keep the onboarding state in the application’s identity domain. Deploy the schema and supporting clients before activating enrollment with one server-side cutoff. Treat accounts verified by activation as established. After activation, classify the first successful verified sign-in atomically under the account lock. A client declaring walkthrough support starts the account at Step 1. A first sign-in on an older client records an exemption so a later upgrade will open Dashboard without introducing a belated tour. The capability marker only selects the UX. Failed sign-ins, verification alone, password resets and further sign-ins leave an assigned state intact. Existing sessions on old clients keep working during rollout.

**Return handoff.** Extend the [web return validator](../../apps/web/src/lib/journey-return.ts) and [native Account return path](../../apps/mobile/src/app/account.tsx) to keep one typed, allowlisted destination for an explicit sign-in request per originating browser tab or device. Capture it before sign-in, attach a proposed 24-hour expiry, and bind it to the verified account when the corresponding sign-in flow succeeds. The Account form or its verification return can resume that unbound flow. An unrelated generic sign-in discards an unbound intent. The verification callback itself remains fixed. A bound handoff can survive walkthrough interruption and same-account reauthentication on that client. Clear it when the target or its unavailable screen opens, when the person explicitly chooses Dashboard, when it expires, or on a confirmed account switch. A new targeted sign-in replaces the previous handoff. Use Dashboard when a target cannot be recovered or validated. Keep raw URLs, bearer credentials and email out of return storage. Reauthorize on destination entry before resuming any protected action.

**Progress.** Each **Continue** confirms the current step and advances one checkpoint. **Back** revisits steps locally. From an earlier step, Continue moves forward through the already cleared steps without a write. On reload resume from the furthest confirmed checkpoint. Send the account precondition on protected reads and writes and scope progress to the current verified session in the transaction. Persist completion before routing and keep it terminal. While a write is pending show a saving state. On error retain the current screen with Retry. Already-confirmed operations return the current state, future-step jumps are rejected, and stale clients re-read it. A lost finish response can use the confirmed result to resume the chosen destination. The final confirmation persists the selected intent alongside completion in the same account transaction. The existing name is read and edited through the verified account profile API. The previous second and third checkpoints both resume on the intent screen. Completed and exempt accounts open Dashboard directly. The guard controls workspace navigation. Domain permissions continue to depend on the existing authorization checks. Keep Account, verification and reset available throughout.

## Dashboard and navigation

The web workspace uses the shadcn Radix sidebar with **Dashboard**, **Journeys**, **Discover** and **Saved**. The active destination has a stronger label and a visible outline, including inside journey routes. The sidebar starts expanded at 80rem and uses an icon rail with tooltips between 48rem and 80rem. Both desktop widths remember the user’s choice independently. Below 48rem, users open a drawer with a keyboard-accessible close button. The footer menu shows the signed-in profile with an option to open **Account**, select one of four appearances in a compact grid, or **Sign out**. On native add **Dashboard** as the first labelled destination beside Journeys, Discover and Saved. Keep the existing Account control. Make Dashboard the authenticated home on all supported clients by the end of the milestone. Keep **Journeys** as the full history and creation destination.

The Dashboard offers the existing journey creation route through one primary action. The illustrated empty state uses the first-journey choice when saved and displays the journey totals. Give the next journey the largest region, then show a compact overview and up to three recent rows. On narrow screens, use the same reading order in one column. Link rows to the canonical journey and **All journeys** to history.

The web shell passes routed content through the layout as a stable React child. Sidebar state lives in the shadcn provider, and the child routes keep their own queries and form state across width changes. [Workspace layout](../../apps/web/src/components/workspace-layout.tsx) · [Sidebar regression](../../tests/web/workspace-sidebar.playwright.ts)

| Region | First release |

| **Overview** | **Journeys** counts distinct journey IDs with current membership, including archived journeys. **Upcoming plans** counts the same non-archived future set used by **Next journey**. For a new account, show the create action and a short explanation of what will appear after creating a journey. For populated accounts, use real totals, a stable loading layout, a retry state for unavailable data, and access-safe refresh on foreground/reentry and after creation. ## Implementation sequence

1. **Agree the surface and examples.** Prototype both setup screens and Dashboard at desktop and phone widths under the approved tokens. Check copy, progress, the small-screen action order and the pending-return path. Record the accepted navigation and first-run rules in the application design and product requirements.
2. **Ship account state and Dashboard summary contracts.** In the identity domain, add the schema ahead of activation, eligibility classification at verified sign-in, and scoped, idempotent progress operations. In the Journey domain, add a bounded Dashboard read reusing the [active membership query](../../packages/backend/src/modules/journeys/service.ts) and schedule rules. Use one snapshot and one `asOf` for the totals and rows. Follow the existing protected [HTTP wiring](../../apps/server/src/http/v1.ts), response and cache rules. Keep API additions compatible with deployed clients.
3. **Implement web.** Add a single routing policy for home, sign-in return and guarded routes. Update the [root shell](../../apps/web/src/routes/__root.tsx), [home](../../apps/web/src/routes/index.tsx) and [account sign-in](../../apps/web/src/routes/account.tsx). Use the existing session provider and return validator as the starting point. Render welcome and intent first, then Dashboard and the updated shell. Bind pending requests and summary data to the active account and clear private data when that scope changes.
4. **Implement iPhone and Android.** Add the same checkpoints, Dashboard and contextual return rules using the [mobile session provider](../../apps/mobile/src/mobile-session.tsx) and [root navigation](../../apps/mobile/src/app/_layout.tsx). Use the approved native controls, safe areas and accessibility text scaling. Keep the content and interaction equivalent across platforms.
5. **Verify, then activate.** Use existing service-backed suites and place new regression fixtures under `tests/`. Record the actual results in this plan and [implementation progress](../progress.md). Activate enrollment once the supported clients are ready. Resume invitations once this milestone is accepted, then connect people data when membership privacy and revocation checks pass.

## Native implementation plan

**Scope.** Bring the two-step setup and the real Dashboard to iPhone and Android with the existing Expo Router stack, mobile account screen, four appearances, and shared design tokens. Reuse the coastal illustrations and journey wording from web. Keep Dashboard, Journeys, Discover and Saved in the native tab bar, with Account outside it. A compact tab layout must keep all four labels usable at large text sizes.

| Area | Existing authority | Native work |
| --- | --- | --- |
| Enrollment and checkpoint | The existing email sign-in transaction checks the capability header and cutoff. GET and POST `/api/v1/onboarding` own eligibility, the pending step, and completion with optional intent. | Add the capability header to native email sign-in only. Read and confirm using the verified scope and generated contracts. Reconcile a conflict or lost reply from the server. Keep local Back and choice state separate from the durable checkpoint. |
| Profile | GET and PATCH `/api/v1/profile` read and update the established display name. | Reuse the native field and action controls and one name editor in setup and Account. Update the same account-scoped query after a save. |
| Dashboard | GET `/api/v1/dashboard` computes the next journey, totals, and recent journeys within current memberships. | Render those fields and reuse the existing history, details and creation routes. Show the saved onboarding action while the account has no journeys. Share web journey-intent copy via the shared package and pass only the existing intent enum to the native creation form. Refresh on entry, foreground, and successful create. |
| Transport and storage | The native account scope already attaches the SecureStore session cookie and expected-account header, pauses writes on revalidation, and cancels work on account changes. | Reuse that transport and cache lifetime for each new query and mutation. Keep a small allowlisted return handoff with expiry and account binding. Never store credentials or arbitrary redirects in it. |

### Navigation and recovery

1. Keep the root navigator mounted. Gate the tab content while the session or onboarding checkpoint is unresolved, with Account reachable to sign in, retry or sign out. Use the actual internal route to capture a supported explicit link before redirecting. Normal launches and sign-ins use Dashboard. Bind a pending handoff at successful sign-in, clear it on a confirmed account switch or expiry, and consume it once the destination opens. A verified user can open Account during setup and return to setup.
2. On foreground revalidation, temporarily conceal private UI and block writes while retaining the same verified account subtree. Do not key tab navigation by transient loading state or change an Expo protected-route guard during foreground checks, since a false guard removes history. A confirmed scope change disposes that account’s queries and private screens. Retry the onboarding query when it fails and show Account as an exit. [Expo Router protected routes](https://docs.expo.dev/router/advanced/protected/) · [Expo navigation](https://docs.expo.dev/router/basics/navigation/)
3. Onboarding starts with Welcome, profile name and Continue, then offers Plan a journey, Record a past journey and Look around. Keep the normal phone reading order, support the keyboard, show the current step, announce step changes, and respect reduced motion. An explicit preserved destination can be opened after confirmed completion. Dashboard shows the matching first action, starts with the next journey when populated, then includes totals and a short recent list. Every action points to the existing canonical journey route.
