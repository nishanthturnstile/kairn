# Import a completed journey from GPX

**Proposed implementation plan · 23 November 2026.** A traveller comes home with a GPX that covers the hike but misses the train home. They can review the hike, enter the dates of the whole trip, and save one private journey. If a companion has already created the journey, they can attach the recording there. In either case, the train journey can remain unrecorded.

The [Create a journey redesign proposal](create-journey-gpx-redesign.md) brings the new-journey entry and multi-file GPX selection together. This plan records the current single-file implementation and its release qualification.

## Outcome and delivery order

Bring one post-trip workflow forward. Build a private, resumable source upload and prove it with a single GPX on responsive web. Use the same server operations for Android and iPhone document selection. A successful import opens the canonical journey detail and works with the map closed. Manual creation, invitations, and history retain their existing paths. A traveller can finish a journey without GPS.

The current sequence puts native field capture and sync in workstream 2, selected imports in 3, and geographic reconstruction in 6. The proposed change brings the shared source and transfer work from 2, the GPX part of 3, and the recorded-segment model from 6 together. A file already in the traveller’s hands exercises all three without camera, microphone or foreground-location integration. Durable native capture, sync, FIT, selected media, and the rest of R1 retain their release requirements. Web completion is an engineering increment. Android and responsive web are the planned initial public clients, with iPhone native qualified locally under the existing distribution plan. ## Select, review and save

1. **Enter from Journeys.** Make **Import GPX** the primary action in empty and populated history on web and native, with the same order on screen and in focus. **Create journey manually** is secondary and opens the existing form and invitation handoff. The import page defaults to **New journey** and offers **Existing journey** through an accessible, paginated picker of eligible destinations. From detail, **Add recording** opens the same flow with that journey selected after the eligibility check. Provide **Change journey** before commitment. Selecting a similarly dated journey always requires a deliberate choice.
2. **Choose the file.** Lead with “Import a GPX recording”, the destination and a labelled **Choose GPX file** control. Show the supported type, current byte limit and “Only you can review this file” before transfer. Show the filename, size, **Upload for review** and **Choose another file** after selection. Cancelling the system picker returns to the prior selection. Drop is an enhancement to the web input. Picker filtering is advisory. Ask only for the selected document. Offer **Create journey manually** if the traveller has no usable recording.
3. **Transfer and inspect.** Base determinate progress on bytes the server acknowledges. Show an indeterminate state when the total is unknown. After checksum-confirmed completion, show **Uploaded privately**. Use **Reading recording** for parsing with one visible status transition and one announcement on entry. Keep the file, destination and any saved corrections on return. **Pause upload**, **Retry upload**, or **Cancel upload** act on this file. Parsing can continue on the server after navigation. An owner-scoped **Resume import** entry on Journeys recovers unfinished work, including an upload that succeeded before its response arrived. Keep a review in progress out of journey history until commit.
4. **Review recording.** Lead with a source-labelled summary and ordered track/segment list. For example, a traveller might read “Morning hike · 2 recorded sections · 6.4 km recorded. Path unknown between sections.” Show warnings beside the affected section. Permit named track/segment inclusion, exclusion, a user-marked break at a sample, and undo before save. At least one usable selected run is required. The optional **Show map** control follows the summary. The list supports every correction with a keyboard or a single tap.
5. **Confirm journey details.** For a new journey show editable title, intended start date and time, optional intended end date and time, and IANA time zone using the current form rules. A track name is an editable suggestion. **Use recorded times** explicitly copies a reliable range into the selected zone for review. Allow manual entry even with timestamp-free geometry. Leave unknown fields blank and preserve the import for later if the required start is unknown. Explain that earlier approach days and later return days can be included. Make clear that the confirmed title and schedule appear to members in journey detail, including when the source is Only me. For attach, show the authorised destination title and schedule read-only. Flag an out-of-range recording and allow the traveller to keep it. Attaching never edits that schedule.
6. **Confirm who can review.** Show **Only me** by default with a named destination. Explain that only the owner sees the linked recording in this state, including after inviting others. An explicit **Journey review** choice describes the audience before save. For an ordinary member it contributes the owner’s recording for review. Only a coauthor with an eligible review grant can also include sections in the shared draft. Keep that placement explicit. Show the selected audience and action together above **Create private journey** or **Add recording**. No invitations or publication on this path.
7. **Open the result.** After server confirmation, open the authorised journey detail, refresh history and show a durable **Recording** section below Schedule and People. It contains the authorised summary, segment list, optional map and applicable **Edit recording**, **Manage access** and **Remove recording** actions. A private receipt says “Journey created. Recording visible only to you” or names the chosen review audience. Provide **Your recordings** under Account on web and native so the owner can recover unplaced and detached originals and recordings from journeys they left. If a save succeeded and the destination is now unavailable, open the owner’s recording with “Recording saved. This journey is no longer available.” Back restores the originating detail or history position when accessible.

## What a recording means

| Input | Normalisation and review behaviour |
| --- | --- |
| GPX 1.0 or 1.1 | Recognise the declared root version and its GPX namespace, including prefixed names. Qualify common namespace-free exports as an explicitly tested compatibility case. Conflicting namespace and version yield an unsupported-file issue. Ignore unknown extension subtrees and external links. Treat names as bounded plain text. |
| Multiple tracks or segments in one file | Preserve original track, segment and point order and stable source indices. Each track segment starts a separate run. Preserve omitted/empty segments in diagnostics. Never join tracks by proximity, day or matching names. Multiple tracks in a file do not establish that they are consecutive legs. |
| Routes, waypoints and mixtures | A recorded path needs at least two usable samples in one continuous run. Route points describe a plan. Standalone waypoints and isolated track points can be listed as observations with no line. On mixed files, import eligible track runs and state the counts of ignored routes and standalone waypoints. A routes-only, waypoints-only, empty or all-singleton file gets a specific explanation and the manual path. |
| Invalid or sparse samples | Require finite in-range WGS84 coordinates. A bad coordinate ends the current run. Keep later valid runs and report skipped counts. Missing elevation or time leaves geometry intact. Preserve duplicate stationary points and their distinct times. A long pause, implausible jump or clock reversal is flagged by the versioned inspection policy. Break a suspect edge pending review and explain its reason. Permit an owner to mark a discontinuity even without reliable times. |
| Time and elevation | Retain source timestamp text, explicit offset, resolved instant when available, nullable elevation in metres and original sample order. Parse date/time with no offset as unresolved local time. Preserve invalid optional fields as diagnostics and missing measurements. File creation/modified dates, upload time, current phone position and metadata-level GPX time cannot fill missing point times. Never infer an IANA zone from an offset or coordinates. |

**Recording measurements.** Compute geodesic horizontal distance in metres from consecutive valid unsimplified points within an included continuous run. Store metres and format km at display precision after summing. Use antimeridian-safe distances and display bounds. Display simplification has its own tolerance/version and retains segment endpoints. Label the main number **Recorded distance** with the selected recording or section. Give each run its own measurement. Sum across runs only when the reviewed evidence establishes distinct traversals. Apply that rule to multiple segments within a single track as well as across tracks. Overlapping or uncertain runs keep individual figures. The same path travelled at distinct verified times may count twice. A journey-wide total depends on accepted primary leg ranges.

For a complete monotone timed run, **Recorded elapsed time** is last instant minus first and includes stops inside the run. Across disjoint runs, show individual values and a total only for complete, non-overlapping timed intervals, excluding gaps. For partial/non-monotone time show known observations with their coverage and leave the duration unavailable. Give elevation min/max from actual recorded samples and show gaps in any profile. Missing data supplies neither zero metres nor a flat line. Defer moving time, smoothed ascent/descent, speeds and inferred transfer distances until the method and labels can be tested. A device recording window and a traveller-confirmed itinerary always have separate fields and labels. History grouping continues to use the confirmed schedule, including its existing open-ended rules.

The batch review shows recorded elevation gain as the sum of positive changes between consecutive measured samples within each included section. Missing elevations make that gain unavailable. Gaps and edits start a new section. Combine totals only for disjoint timed runs, and count identical originals once. For older staged files, a batch with one distinct original can recover the gain from its sample pages.

**Owner review.** Keep the original bytes and each normalisation revision immutable. Store owner corrections as a new recording revision with the base revision, author, selected ranges, splits, exclusions and any corrected local time, zone or clock offset. Preview the changes and offer reset. A display-zone change preserves known instants. A device-clock correction requires an explicit shift and preserves the original observation. Resolve ambiguous and skipped local minutes with the existing schedule rules. On reparse, map choices by stable source indices and flag choices that need review. The owner’s latest revision appears in **Your recordings**.

**Journey placement.** A coauthor with placement rights chooses a permitted subset of runs for one journey. Pin the placement to the accepted owner revision and source ranges. Its map, list and metrics use those same inputs. A later clock correction or editorial exclusion is available for explicit acceptance, with the previous accepted revision in use while access permits. Where ranges cannot be mapped safely, require review before acceptance. To remove evidence for privacy, use **Manage access** to narrow or withdraw permission. The restriction takes effect immediately on every affected placement, including pinned revisions. Corrections to the recording leave confirmed journey dates intact. ## Proposed data and API contracts

These operations extend the versioned API. Use the shared schemas and generate client types from the Hono OpenAPI routes. Enforce verified session, expected-account and current source/journey policy on every operation. Browser mutations use the existing origin checks. Private reads use private no-store responses.

| Proposed operation under `/api/v1` | Request, result and retry behaviour |
| --- | --- |
| `POST /uploads`, `GET /uploads/{id}` | Begin an owner-private GPX upload with stable device/command ID, byte length and expected whole-file hash. Return an opaque upload ID, part size, expiry, policy limits and acknowledged parts. Bind immutable upload metadata to its owner. Identical begin replays its receipt. Status reconciles acknowledged parts after reconnect. |
| `PUT /uploads/{id}/parts/{n}`, `POST /uploads/{id}/complete`, `DELETE /uploads/{id}` | Stream authorised bounded parts with length and per-part SHA-256. A matching retry returns the same acknowledgement. Conflicting bytes at one index fail. Finalise the exact contiguous manifest and verify whole-object length and SHA-256 at the store. In one PostgreSQL transaction resolve the canonical owner source and asset, persist the import and completion receipt, and enqueue any processing or redundant-object cleanup. Abort or expire unfinished parts and release reservations once their data is reclaimed. |
| `GET /imports`, `GET /imports/{id}`, `GET /imports/{id}/segments` | Owner-only pending/recoverable list and status. The completed upload identifies one import. Return version, stage, safe file diagnostics, source metadata, counters, limits, cursor and retriable status. Page segments/samples, serve simplified overlays on demand. Keep bulk geometry out of status/history payloads. |
| `GET /recording-attachment-destinations`, `GET /recording-attachment-destinations/{journeyId}` | Page the actor’s eligible unarchived journeys, including those where they are an ordinary contributor. Return the visible title and schedule, actor membership generation, allowed scopes and whether the actor can place a recording in the shared draft. Use the same eligibility and response for the detail entry and direct journey selection. Use the existing authorised source read for any grant or placement revision that applies to the chosen recording. |
| `PATCH /imports/{id}/review`, `POST /imports/{id}/commit` | Save a review revision with selected ranges and evidence corrections. Commit takes that revision, exactly one destination variant, explicit scope and placement intent, and the stable command identity. New carries the journey form payload. Existing carries journey ID, membership generation and applicable placement/grant revisions. Persist stable IDs and outcome in the receipt. Project the result under current access on every read or replay. |
| Journey recording reads and edits | Add scoped list/detail under `/journeys/{id}/recordings` with revision-checked placement edits and detach. Return only authorised rows and measurements. Use the existing journey-scoped source review operations for grant changes and withdrawal. |
| Owner recording reads and edits | Under `/account/recordings`, add an owner-only paged list, detail, revision editing and original download with Range support. Authorise by verified account and source ownership. With no current journey access, omit that journey’s ID, title and schedule from lists, detail and receipts. Add a permanent deletion operation once source-wide restriction and restore are verified. |

Use the existing Problem Details envelope. Return a generic 404 for an inaccessible destination, 409 for a consumed import or mismatched command, 412 for stale revisions or membership generation, 413 for an input limit, and 429 with retry guidance for throttling. A 412 can include a currently permitted revision for comparison. If membership ended and restarted between selection and save, clear the stale selection and ask the traveller to choose again under the new membership. An accepted parse job reports pending until a status read supplies a ready result or a typed processing issue.

**Persistence and job boundaries.** Add migrations for upload sessions/parts/reservations, verified object metadata on or keyed by asset, import state/review revisions, recording tracks/segments/raw samples, selected sample ranges, source-dependent display geometry and operation receipts. Reference the existing source and owner with foreign keys. Link the recording to a journey through an owner association and separate grant/optional editorial placement. Keep sample ranges available to multiple future chapters and travel legs. Use PostGIS for continuous runs, points for observations and a versioned display simplification. Bind derived payloads to asset hash, parser version, review revision and policy generation. Old journeys with no recording keep working. Keep runtime access to sensitive tables behind scoped operations. [Architecture](../core/architecture.md) · [Existing source schema](../../packages/backend/src/modules/sources/schema.ts)

**Boundaries for untrusted files.** Start qualification with the architecture’s proposed 50 MiB / 500,000 accepted point limit, 8 MiB parts and two concurrent parts per device. Also bound input point elements examined, XML depth, strings, output bytes, segment count, wall time, memory and scratch disk before materialising large trees. Advertise enforced limits consistently at edge, gateway and client. Use the architecture’s isolated GPX normaliser with a bounded XML preflight, disabled entities, DOCTYPE rejection and no external resource resolution. Reject unsupported archives and malformed or truncated XML as a whole. Salvage valid runs only in a structurally complete document. Parser subprocesses receive bounded local input and no credentials or network. Record redacted operation IDs, outcome classes, sizes and durations. Keep filenames, point samples, coordinates, source text and object keys out of telemetry and error reports. [Processing limits](../core/architecture.md#155-proposed-numerical-starting-limits)

**Two durable boundaries.** Store completion and database commit can fail independently. Reserve a server-generated object key, reconcile a completed object under that key after a crash, and verify it before asset activation. Enqueue parsing in the same transaction as verified metadata. Parse once logically per verified asset/hash and parser version. A duplicate job reuses its typed result. Before attaching results, recheck state, generation and deletion. Never hold a journey transaction open while reading bytes, parsing or waiting on an external service.

**Verified asset reuse.** Resolve one canonical GPX source, original asset and recording per owner, verified length and digest. Bind pending uploads to the opaque owner asset identity and policy generation for the declared digest. At finalisation, verify the bytes and recheck that generation so a pre-deletion upload cannot activate a new source. Independent uploads each keep their own completion receipt and import draft. Atomically link each to the canonical IDs. Convert only the winning upload’s reservation to retained asset usage. Persist cleanup for a redundant staged object after verifying the canonical object. Release its staging reservation once cleanup succeeds. Retries reconcile the verified object, receipt and cleanup job, and cleanup checks that it still targets the losing staged key. Hash comparison stays within the owner account. [Source and asset reuse](../core/architecture.md#94-action-requests-metadata-and-bounded-recovery-flows)

**One final save.** Within a single database transaction lock the import/receipt and affected destination or placement, recheck ownership, current membership, archive status, source grant revision and coauthor rights where needed. For new, reuse the transactional private-journey creator, creator membership/capabilities and schedule resolution. For existing, retain the destination ID. Write the association, exactly the chosen grant and eligible placement, dependent revisions, generations, audit and receipt together. Only shared draft changes advance its generation. A failure rolls back these effects together and leaves the verified owner import recoverable. Before multi-recording comparison lands, allow independent attachments, show each in its own authorised recording row and never automatically replace a track or sum recordings. This also protects the existence of other owners’ private attachments. A unique consumed-import constraint applies across devices, with uniqueness on owner, destination and verified content for an attachment. Handle competing new/attach commands for the same import under that constraint.

Persist the precise commit payload and key before sending. A lost reply replays that payload and key and returns the stored outcome under current access. Changed payload under that key conflicts. A new command against the same consumed import returns its authorised prior result or a generic conflict. If two import IDs race to attach the same recording in one journey, both receipts identify the same canonical recording and winning association. The second reports **Already added** with the current permitted scope. It leaves placement, review and grant changes to their own explicit controls. Replays after withdrawal preserve the historical outcome and reflect current access. When replay follows departure, return the completed owner result and the personal recording route while suppressing the inaccessible destination.

For an explicit new journey, offer to open an accessible prior result before creating a distinct event. A deliberate reuse in another journey can keep the canonical original and recording. It requires a fresh destination and audience choice, with any new grant and placement scoped to that journey. Similar files are insufficient to identify a shared event. ## Rights, interruption and recovery

- **Delivery.** Before commit, only the verified owner can inspect the upload or preview. After commit, Only me has no active source grant. A journey review grant permits the owner plus active coauthors and designated publishers to see authorised derivatives. All active members retain their existing basic journey detail access. Admin-only and participant membership confer no review-pool access. A publisher role alone confers no placement or editing rights. No count, bounds, file label, accessible description or aggregate may disclose another owner’s private source. Download of original bytes, including Range, requires owner rights or the existing exact recipient/asset export authority at delivery. Keep object keys private.
- **Detach and withdraw.** “Remove recording from journey” shows the affected placement and review audience. Remove the association and placement, withdraw any active grant through the existing restriction path and invalidate dependent reads. The original remains in **Your recordings**. A coauthor can remove an editorial placement within that journey. Losing membership ends contributions while the account-scoped owner route keeps the original recoverable.
- **Delete original.** Explain the impact across every destination and any residual backup retention before confirmation. Extend the restriction journal with a source-wide deletion event carrying opaque source/asset IDs and a policy generation. In one transaction, authorise ownership, persist the tombstone and audit event, deny original and derivative reads across owner and journey routes, and enqueue invalidation, journal append and cleanup. Resolve affected placements from authoritative references, including any recovered during restore. Deny range delivery, reuse, new grants and activation from stale upload, parse or publication jobs. Invalidate cached geometry, metrics, exports and dependent placements on every managed surface. Report pending recovery confirmation until the independent journal acknowledges the event, then confirm deletion and purge eligible bytes according to retention. Replay the tombstone before protected reads or old jobs resume after restore. Expose **Delete original** only after this path has passed a pre-deletion checkpoint restore with a never-shared file. [Backup and restore](../core/architecture.md#154-backup-restore-and-release)
- **Local and server truth.** Track local staging, transfer, parse, review, source scope and publication separately. Show “Saved on this device” only after bytes and metadata are durable, “Uploaded privately” only after verified completion and “Recording added” only after commit. Independent backup requires its own verified checkpoint. Reconcile abandoned multipart sessions, reservations, partial local copies and unreferenced staging outputs. Keep an owner’s last confirmed local original unless they explicitly elect to remove it under the retention policy.
- **Resume.** Web stores account-bound file/handle availability, session IDs, parts, review and pending commands in IndexedDB subject to browser limits. On eviction or reload, reselect the matching bytes when necessary and resume from server acknowledgements. Native stages the document in persistent app-owned files, records verified size/hash and a SQLite outbox in the account namespace, repairs interrupted copies on startup and resumes in foreground. An expiring provider URI or cache path alone is insufficient. Honour Wi-Fi preference and show cloud-provider waits. On sign-out cancel dispatch, clear rendered and cached shared data and quarantine pending work for the same returning account. Recover on another device from the owner’s verified server import. [Capture and sync](../core/architecture.md#82-sync-protocol) · [Import interactions](../core/application-design.md#4-capture-and-import)
